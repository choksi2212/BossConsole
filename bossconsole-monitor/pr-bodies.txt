## Summary

Fixes #873

Three security vulnerabilities in `SnapshotManager`:

### 1. Path Traversal via Unvalidated `processId`

`snapshotDir()` constructed paths via `File(dataDir, "snapshots/$processId")` with no validation. A `processId` like `../../etc` escaped the snapshots directory, allowing:
- Arbitrary file creation (`save()`)
- Arbitrary file deletion (`cleanup()` lists `.snapshot` files and calls `file.delete()`)
- Arbitrary file reads (`loadLatest()`, `listSnapshots()`)

**Fix:** Validate `processId` against `^[A-Za-z0-9_-][A-Za-z0-9._-]{0,199}$` (rejects path separators, double-dots, blank strings, trailing dots). Additionally verify the canonical resolved path stays within the snapshots base directory (defence in depth). Read-only operations (`loadLatest`, `listSnapshots`, `cleanup`) use `resolveSnapshotDir()` which returns `null` for invalid IDs instead of throwing.

### 2. Non-Atomic File Truncation

`save()` used `writeBytes()`/`writeText()` directly, so a crash mid-write left a truncated `.snapshot` file. `loadLatest()` picks the max-timestamp file, meaning recovery would select the corrupt partial file and fail.

**Fix:** Write to a temp sibling (`.name.tmp`) first, then atomically move into place via `ATOMIC_MOVE` (with `REPLACE_EXISTING` fallback for cross-volume on Windows). The target file is never visible in a partial state.

### 3. Umask-Inherited Permissions

Snapshot files (which may contain sensitive process state, environment variables, or config) were written with default umask permissions (0644), readable by other local users on multi-user systems.

**Fix:** Create temp files with POSIX owner-only permissions (`rw-------`) via `Files.createFile` with a `PosixFileAttribute`, and re-assert 0600 before the move. Non-POSIX platforms (Windows) silently skip the permission setting.

## Description

Closes #813 (production scope per the #814 review's recommended handoff — this is the replacement for #814's original branch).

The #814 review was right on both counts: the legacy `refresh()`/`clear()` pair has **no production callers**, and the real cross-window race is in **`refreshForWindow`** and **`alignCurrentProjectPath`** — both wrote the shared GLOBAL `currentProjectPath` from any window's coroutine with no ordering, and a refresh started before a project switch and finished after it repointed the global at a project the user had already left (the file/ref diff verbs then read the wrong worktree — the exact two-worktree `git restore` misdirection the code's own comments describe).

**The fix — a monotonic project epoch, exactly the review's recommended shape:**

- `refreshForWindow` captures the epoch at entry and publishes the global seed **only under the mutex and only if the epoch is unchanged** — a switch that landed while the refresh waited (or while its git subprocesses ran) bumped the epoch and the stale publish is dropped. The window-scoped `WindowGitState` still refreshes; only the global seed for the diff verbs is refused.
- `alignCurrentProjectPath` is the **switch verb** and always wins: it bumps the epoch and writes under the same lock, non-suspending per the expect signature.
- The unused legacy `refresh()`/`clear()` surface keeps the first pass's mutex but its KDoc now states it has no production callers (kept for the top-bar path) — no longer presented as the fix.
